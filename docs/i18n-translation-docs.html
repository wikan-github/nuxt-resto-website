How the translation (i18n) system works

Nuxt-Resto-Website · i18n-translation-docs · 2026-10-17

1. Overview

The site is bilingual (English + Indonesian) via @nuxtjs/i18n v10.6 — the only Nuxt module in the project (nuxt.config.ts:134). All translatable copy lives in two JSON files, keyed by nested namespaces.

ItemValue
Module@nuxtjs/i18n 10.6.0
Localesen (default), id
Filesi18n/locales/en.json, i18n/locales/id.json
Strategyprefix_except_default
Loadinglazy: true — only the active locale is downloaded
Persistencecookie i18n_lang
Config locationnuxt.config.ts:108-131

2. URL strategy — prefix_except_default

The default locale gets no prefix; every other locale does:

LocaleRoute
EN (default)/menu
ID/id/menu
Do not create pages/[lang]/. The module already owns the locale prefix. A file at app/pages/monkey-forest-exit.vue automatically serves both /monkey-forest-exit and /id/monkey-forest-exit.

3. Looking up strings

There are two syntaxes, and using the wrong one in the wrong place is the most common mistake:

WhereHowWhy
Template{{ $t('nav.menu') }}$t is injected into template scope by the module (~230 call sites)
<script setup>const { t } = useI18n() then t('nav.menu')$t is not available in script — only t

This distinction is documented in app/pages/monkey-forest.vue:185.

Both are reactive: switching locale re-renders every $t in place, with no page reload.

Lazy loading (lazy: true) means only the active locale's JSON is fetched — an EN visitor never downloads id.json. A side effect: a key missing from one file does not throw, it simply renders the key path as visible text.

4. Switching language

app/components/LanguageSwitcher.vue loops the configured locales and calls setLocale():

const { locale, locales, setLocale } = useI18n()
// <button v-for="loc in locales" @click="setLocale(loc.code)">EN / ID</button>
  • setLocale(code) updates the URL and the rendered copy.
  • The choice persists in the i18n_lang cookie.
  • detectBrowserLanguage.redirectOn: 'root' — browser-language detection only fires at /; deep links such as /id/menu are never auto-redirected.

5. Locale-aware links — known bug

Bug: @nuxtjs/i18n does not auto-prefix a plain <NuxtLink>. Verified: NuxtLinkLocale is used nowhere in this repo, and localePath() appears in exactly one place (NavBreadcrumb.vue:139).

Live proof — the header nav rendered on /id/:

['/', '/menu', '/promotions', '/monkey-forest', '/about', '/contact']

So an Indonesian visitor on /id/ who taps header “Menu” is sent to /menu — silently switched back to English.

Affected files

  • app/layouts/default.vue — 6 nav links + logo (the whole header)
  • app/pages/index.vue — CTA buttons
  • app/pages/about.vue — CTA buttons
  • app/components/campaign/HeroAfterMonkeyForest.vue — “See menu” CTA

Correct pattern

Already used in NavBreadcrumb.vue and monkey-forest-exit.vue:

const localePath = useLocalePath()
// :to="localePath('/menu')"  →  '/menu' (EN) or '/id/menu' (ID)

Fix = swap <NuxtLink to="/x"> for <NuxtLink :to="localePath('/x')"> (or use <NuxtLinkLocale>) in the affected files.

6. Related gaps

  • nuxt.config.ts:62 hardcodes htmlAttrs: { lang: 'en' }, and no useLocaleHead() is called anywhere — so <html lang> stays "en" even on /id/.
  • No hreflang alternates are emitted (i18n.baseUrl is unset), so search engines get no EN↔ID signal.

7. Adding strings

  1. Add the key to both en.json and id.json with identical structure.
  2. Keep namespaces per-feature (nav, hero, campaignOffer, monkey_forest_exit, …).
  3. Reuse an existing namespace before creating a new one.
  4. Verify parity with a key-diff — asymmetry is the failure mode this convention exists to prevent.

Every locale change must be logged in handoffs/i18n.md under ## Changelog.
